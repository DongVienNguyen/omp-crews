name: crew-omp
description: Plan and execute a Crews team through OMP native task with admitted configurable Combo model and effort.
---
Read crew_catalog before planning: it exposes the canonical minimal_example, role schema, questions rubric and role-kind columns. crew_plan uses spec.task and spec.roles with name, kind, mission, deliverable, scope, acceptance (criteria for check), and nested answers. Never invent goal/id/task/model aliases for role fields. Task answers belong in top-level answers; per-role answers in spec.roles[].answers. Supply absolute project path and a unique session label. If validation fails, correct the named fields and retry crew_plan, never substitute an ordinary task. The runtime blocks native delegation while a plan is pending/failed; a corrected valid plan clears it. A new user prompt resets that turn-local gate so unrelated work is not locked. Ordinary factual chat needs no crew; substantive delegated work should use a crew rather than generic task.

Use Combo Small/Medium/Large, not model-specific seat names. Active policy.json assigns each Combo a user model ID and effort Low/Medium/High/Auto. Omitted effort is Auto. Small handles mechanical_verification, repeatable_task and bounded_retrieval; Medium handles everyday_implementation and long_running_agentic; Large handles difficult_review, integration_architecture and specialist. Auto effort is computed independently from each role difficulty: d<1 low, 1<=d<2 medium, 2<=d<=3 high. Explicit Low/Medium/High overrides Auto. Native wire values are lowercase; Auto is never sent to provider. Main model stays unchanged; do not force Combo selection with a model name in role answers.

Interactive `/crew combos` lets user select Combo, edit provider/model and choose effort with confirmation. Headless `crews-omp combo show|set|reset` writes the same validated policy. Provider/model capabilities and credentials stay in OMP. Same model may serve several Combos. Policy updates require fresh plans; no cached ticket is reclassified or silently repaired after configuration changes.

Classify each role by its deliverable, not by the hardest part of the whole project. Difficulty 0: one obvious step; 1: familiar known method; 2: ambiguity/tricky reasoning; 3: strong attempt might fail. Exact target/method/values already fixed and a changed artifact means repeatable_task. A deterministic pass/fail against stated criteria means mechanical_verification. Information about existing material means bounded_retrieval. Open behavior decisions mean everyday_implementation; unknown-cause diagnosis/high-stakes judgment means difficult_review; undecided cross-system seams mean integration_architecture. Use the complete catalog rubric for edge cases.

When a larger task naturally separates: Seek research gathers named files/callers/log facts; Sol/Astra resolves uncertain causes or behavior; Seek produce applies only exact prescribed edits; Seek check verifies deterministic acceptance. Do not add redundant agents for trivial one-step work. Keep check blind: pass artifact paths/criteria, not producer conclusions. Use fresh per-role answers with observable acceptance. Routing metadata in each plan stores task_answers, role_answers, routing_reason and dispatch_path for audit.

The session transcript stores crews-routing entries distinguishing main, native-task (no Crews remap), and crew (admitted model/effort/reason). Main Sol messages are not evidence that delegated work ran on Sol. Read crew_results wire/native evidence before claiming execution.

Use `/crew combos` for user configuration; `/crew status`, `/crew test <role JSON>`, `/crew history`, `/crew reload` or crew_preview for bounded diagnostics. Previews create no plan/ticket/child. Native main/task paths remain unchanged unless canonical intake is selected.

For auto classification use `task {intake:{spec:{task,roles:[...]},answers:<task answers>,session:<unique>}}`. Every role needs name/kind/mission/deliverable/scope/commands/acceptance (criteria for check), answers.divisible and answers.specific. Set classification:true to resolve missing need/difficulty from optional solution_space and strict tri-state facts: method_fixed, targets_fixed, information_only, criterion_fixed, behavior_undecided, unknown_cause, consequential_judgment. Missing facts mean unknown. Explicit need/difficulty wins unless contradicted by safety facts; unknown cause/consequential judgment cannot be labeled cheap. Intake returns a validated plan only; dispatch its exact crew references afterwards. Never create scope/criteria from plain task text or reclassify a ticket after admission.

Classifier settings live in state classifier.json: recommend(default), shadow, off. For unresolved classification:true roles the teacher uses configured Large Combo (Auto classifier difficulty3, high), timeout30000ms/output512-token cap. Declared/deterministic answers bypass AI except explicit shadow comparisons. Teacher only proposes need/difficulty, never execution authority. Errors require classification; no silent fallback.

Verified learning is project-scoped and shadow by default. Exact task/context/policy fingerprints only; no fuzzy cheap downgrade. Inspect with read-only crew_learning or CLI learning report/observations/rules. Only the user can label verified need/difficulty through /crew learning confirmation or CLI --yes with independent unit IDs/evidence. Never label model self-COMPLETE or provider timeout as correctness. Candidate requires3train+2disjoint holdout; activation and on mode explicit. Every10active hits audit Large fresh, errors/disagreement suspend; rollback supported. Do not bypass safety facts or authority via learning. Learning DB stores HMAC fingerprints/safe facts/metrics, not raw task/evidence; normal Crews transcripts/records still have their ordinary content. Preview creates no training observation.

Portable install: use `omp plugin link <checkout>` or install a verified packed artifact, then `crews-omp setup --python <Python 3.12+ executable>` (see CLI help). Existing manual installation uses migrate --dry-run before migrate. Doctor verifies runtime/MCP/aliases without credentials. Do not run system pip, copy old personal runtime.json, auto-download Python or publish without user authorization. Preserve state and historical run counters. Startup on Windows after package changes requires a new OMP process.

OMP admission accepts only the active Combo provider/model/effort bindings, including stored plans. The legacy Codex path is removed. Historical records are not rewritten. Repair keeps the same Combo/effort; explicit escalation moves Small -> Medium -> Large, using the target Combo's configured effort or Auto at the same role difficulty. Large has no stronger configured Combo. Caps remain two repairs/four escalations per run. Do not bypass caps by replanning unchanged failed work; new plans are for changed scope/artifacts or explicit user-directed recovery.

The local Python bridge uses UTF-8 stdin/stdout explicitly on Windows, including Vietnamese briefs. The offline check includes dispatch under a cp1252 process environment; keep this boundary independent of the terminal code page.

Bridge failures expose the Python reason as `Crews bridge <operation>: <reason>`. `prior role evidence stale: <path>` is an admission refusal, not a model/provider failure: an earlier producer artifact changed after its recorded verification. Do not overwrite stored fingerprints, mark a planned checker COMPLETE, retry escalation to evade the guard, or switch to generic delegation. Reconcile the changed artifact and create a fresh explicitly scoped plan/check against current files with the original acceptance criteria. Launch was not successful without native/wire evidence. `check_bridge_launch.py` exercises escalated admission, stale-artifact refusal and error propagation without provider calls.

Each role has explicit project-relative scope and optional commands (exact test command strings). Producer/integrator may write only declared files. Check/research may run explicitly admitted commands but must not edit. Scope checks are extension checks, not an OS sandbox. Shell commands must be narrowly defined; avoid arbitrary shell commands or scripts writable by the producer when granting a read-only checker authority.

Role briefs include an `admitted_commands` JSON list. Copy an exact string from that list; never guess wrapper filenames, append echo/cd, or treat commands stored outside the prompt as visible authority. If a numeric subprocess exit is required but shell metadata omits it, the orchestrator must explicitly admit a pre-verified wrapper that prints and returns the real child exit status; absent diagnostics alone is not proof of exit0.

After the plan is reviewed as required by the user's request, invoke task with only crew:{run:<run_id>,role:<role_id>,session:<same label>}. The adapter admits and launches that role; do not call crew_admit or manually register a fake result. Read task evidence and crew_results before advancing waves. Use fresh child roles for independent checks, with original acceptance criteria; do not place producer conclusions in checker context. Do not call eval/workpool/vibe/clone to bypass this path.

COMPLETE requires actual verification, a matching model/effort receipt and successful strict structured output. Failed roles require an explicit crew_escalate repair/escalation with bounded reason. Max two repairs/four escalations per run, depth one. Never claim success for PARTIAL/BLOCKED/FAILED. A technical review does not grant permission for external publishing or destructive actions.

If host native delegation is missing, old auto-router is still loaded, or model evidence fails, stop crew execution and report the reason. Keep unrelated OMP usage available. Existing incomplete runs must not auto-replay after restart; create a new plan or explicitly repair a recorded failure.
